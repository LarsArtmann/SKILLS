# Deduplicate Code

## Principle

Duplication is a smell, not a sin. A clone detector finds _similar text_; you
must decide whether that similarity is a real maintenance burden or an
acceptable, idiomatic pattern. Do not reflexively extract abstractions. Every
duplication you remove should make the codebase easier to change.

## Decision Checklist (apply to every clone group)

Before refactoring, answer these questions:

1. **Is the code generated?** → Exclude it. Never edit files marked
   `Code generated by` or `DO NOT EDIT`.
2. **Is the similarity structural or semantic?**
   - Same logic, different names → likely refactor.
   - Same shape, different intent → likely leave alone.
3. **Would an abstraction improve or harm readability?**
   - If the shared code has a clear domain name → extract.
   - If the abstraction would take more parameters than the duplicated code has
     lines → leave alone.
4. **Is the duplication likely to drift?**
   - Two places that must change together → extract.
   - Two places that happen to look similar now → leave alone.

## Run the Analysis

Use the threshold the user tells you. If none was mentioned, use `-t 15`.

```bash
art-dupl --semantic --sort total-tokens -t 15 \
  --exclude-pattern "**/generated/**" \
  --exclude-pattern "**/generatedconnect/**" \
  --exclude-pattern "**/internal/generated/**" \
  --exclude-pattern "**/internal/api/openapi*" \
  --exclude-pattern "**/persistence/db/sqlite/**"
```

### Threshold selection

- **15 (default)**: Aggressive scan. Catches small helpers and repeated snippets,
  but will also surface Go idioms (`if err != nil`, function signatures, error
  returns). Use the decision checklist to filter idioms from real clones.
- **30–40**: Catches medium-sized helpers and repeated logic. Expect fewer
  structural matches.
- **50+**: Only large, obvious clones. Good for a first pass on a messy codebase
  or when time is limited.

If a run produces too much noise at `-t 15`, do not blindly raise the threshold.
Instead, review the results, mark idiomatic patterns as accepted, and ask the
user whether to raise the threshold or add exclusions for noisy paths.

## Handle Each Clone Group

For every reported group:

1. Read the files and lines involved.
2. Decide: **extract**, **exclude**, or **accept**.
3. If extracting: create a well-named helper, update all call sites, and run
   tests.
4. If excluding: add the narrowest `--exclude-pattern` that covers the case and
   document why in a comment near the exclusion or in the PR description.
5. If accepting: record a one-line rationale so the next reader knows it was
   intentional.

## Generated Code

Generated files must never be manually de-duplicated. Add exclusions:

- Protobuf / connect-go: `--exclude-pattern "**/generatedconnect/**"`
- sqlc output: `--exclude-pattern "**/persistence/db/sqlite/**"`
- Stringer / mockgen: already covered by `**/generated/**`
- OpenAPI / Swagger: `--exclude-pattern "**/internal/api/openapi*"`

## Test Code

Do not blanket-exclude `*_test.go`. Evaluate each group:

**Refactor when the duplication is a real burden:**

- Shared setup, teardown, or fixtures used across multiple packages
- Identical HTTP handler boilerplate (router, recorder, request construction)
- Repeated test-data builders or factory functions
- Copy-pasted assertion sequences that could become a custom matcher

**Accept when the similarity is idiomatic:**

- Table-driven test tables (same shape, different data)
- Standard Ginkgo / Gomega assertions (`Expect(err).ToNot(HaveOccurred())`)
- Per-test setup that differs by one or two lines

## Definition of Done

You are done when the codebase has **zero harmful duplication**. That does not
mean the clone report is empty. It means every remaining clone is there on
purpose.

**Done looks like this:**

- Generated code is excluded, not modified.
- Every extractable clone with shared semantics has been pulled into a clear,
  well-named helper.
- Every remaining clone has a one-line rationale (in a code comment, exclusion
  note, or PR description).
- All tests pass and behavior is unchanged.

**Stop earlier only if:**

- Removing a clone would require an abstraction more complex than the
  duplication itself.
- The remaining similarity is a domain-specific intentional variation.
- The user explicitly changes scope or threshold.

Zero harmful duplication. Not zero report lines.

## ADR-Style Policy (Project-Specific)

If the project has a duplicate-code ADR (e.g. `docs/adr/001-duplicate-code-policy.md`),
prefer its rules over the defaults above.

**Generally accept duplication when:**

- Different business rules or domain contexts
- Different test scenarios or test-data shapes
- A type-safe abstraction already exists and is used correctly
- The duplicated form is more readable than the abstraction
- Domain-specific logic that looks similar but serves different purposes

**Generally eliminate duplication when:**

- Implementation is identical with no type-specific behavior
- Multiple functions exist for the same purpose
- Changes must be made in N places to keep behavior consistent
