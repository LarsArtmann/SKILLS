1. Current State

The SKILLS repository contains 18 skill directories, each with a SKILL.md file and optional subdirectories. The entire data model is implicit — encoded in directory names, YAML frontmatter conventions, and markdown body structure. There is no schema, no validation, and no machine-readable relationships.

2. Problem Catalog

Each problem is graded by severity (how much damage it causes) and systemicity (how many skills it affects). Problems with high systemicity are force multipliers — fix them once, improve everything.

P1 — No Formal Schema

Critical

The only "schema" is how-to-write-skills.md — a human-readable guide. Frontmatter fields are not validated. A skill can have a description that is documentation instead of a trigger, and nothing catches it. A skill can claim name: foo while living in directory bar/, and nothing catches it.

TypeScript fix: Branded types SkillName and FilePath + a ValidatedSkill type that encodes __directoryMatchesName: true at the type level.

P2 — Stringly-Typed Everything

Critical

tags is a comma-separated string, not a typed array. status doesn't exist as a field — it only lives in README.md tables and audit docs. Quality grades like "thin" / "solid" / "comprehensive" have no enum definition. The features-audit skill even contains a typo: PARTIALLY_FUNTIONAL — impossible with a real enum.

TypeScript fix: enum SkillStatus { Draft, Thin, Solid, Comprehensive } + ReadonlyArray<string> for tags. Make invalid states unrepresentable.

P3 — Monolithic Skills

High

Skills are atomic blobs of markdown. There is no way to compose a skill from reusable fragments. The "READ, UNDERSTAND, RESEARCH, REFLECT" execution boilerplate is copy-pasted into 6+ skills. When it changes in execution-mode, the other 5 become stale. This is the textbook definition of a DRY violation.

TypeScript fix: ProcessFragment<TIntent> as a composable unit. Skills reference fragments by ID rather than inlining them. Update the fragment once, all consumers get the new version.

P4 — No Dependency Graph

High

Cross-references between skills are just markdown links in prose. "For Go ecosystem libraries, use the how-to-golang skill" — this is not machine-readable. We cannot answer: "Which skills would break if how-to-golang is removed?" or "What is the transitive closure of skills needed for a Go project?"

TypeScript fix: relationships: { requires?: SkillName[]; references?: SkillName[]; conflictsWith?: SkillName[] } — a directed, typed dependency graph.

P5 — No Versioning or Lifecycle

High

Skills have no version, no createdAt, no updatedAt, no deprecated flag. The comprehensive audit had to manually count lines and guess quality. There is no way to know if a skill is actively maintained or rotting. The originals/ directory exists because there is no deprecation mechanism.

TypeScript fix: version: SemverString + createdAt: Date + updatedAt: Date + deprecated?: Date. Derived types can filter active vs. stale skills at compile time.

P6 — Manual Catalog Maintenance

High

The README.md skills table is maintained by hand. It claims 18 skills while the comprehensive audit found 15. It claims 8 are thin while the audit found 9. The "Quick Start" section has installation instructions that will install dead legacy files. Any schema change requires touching N files.

TypeScript fix: type SkillCatalog = Record<SkillName, Skill> + a single source of truth. README, audit docs, and trigger indices are all derived views generated from the catalog via mapped types and utility functions.

P7 — No Validation Layer

High

There is no tool that validates: "Does the name in frontmatter match the directory name?" "Does every references/go-ecosystem.md link point to an existing file?" "Are all SkillName references in relationships resolvable?" The audit found broken references and mismatched names entirely by manual inspection.

TypeScript fix: A ValidatedSkill intersection type that requires proof of structural and referential integrity. Validation becomes a type-level concern, not a runtime afterthought.

P8 — No Empirical Testing Metadata

High

Skill descriptions are "educated guesses." None have been tested in Crush's actual triggering mechanism. The skill-creator skill has an optimization loop, but there is no structured place to store test prompts, expected activations, or accuracy scores.

TypeScript fix: empiricalTests: Array<{ prompt: string; expectedSkill: SkillName; triggered: boolean; accuracy: number }> — first-class testing data attached to the skill itself.

P9 — No Environment Requirements

Medium

architecture-visualization needs d2 CLI. deduplicate-code needs art-dupl. naming-review needs revive. None of this is declared. The skill just hardcodes commands and hopes the binary exists. There is no fallback strategy, no version constraint, no installation guidance.

TypeScript fix: environment: { requiredCLIs: Array<{ name: string; minVersion?: SemverString }>; optionalCLIs: Array<{ name: string; fallback?: string }> }

P10 — No Output Schema

Medium

Skills that produce structured output (pareto-planning writes D2 execution graphs, status-report writes markdown tables, features-audit writes FEATURES.md) have no formal schema definition. The output format is described in prose, not in a machine-checkable structure. Only 2 of 15 skills have any output template.

TypeScript fix: outputs: { format: 'markdown' | 'html' | 'd2' | 'json'; schema: unknown; template?: FilePath; examples?: unknown[] }

P11 — Weak Resource Typing

Medium

scripts/, references/, rules/, assets/ are just directories. A reference file has no metadata about its topic, size, or whether it includes a table of contents. A script has no metadata about whether it is executable or what it does. The agent must read the file to discover this — wasting context tokens on irrelevant files.

TypeScript fix: Discriminated union Resource = Script | Reference | Rule | Asset with rich per-variant metadata. The agent can filter resources by kind and topic without reading the file.

P12 — No Generic Parameterization

Medium

naming-review has language-specific inline tables for Go, TypeScript, Rust, Python, Java, and C#. This should be a generic skill parameterized by <TLanguage> with language-specific rules loaded from references/<lang>.md. Currently, adding a language requires editing the skill body. With generics, it requires adding one reference file.

TypeScript fix: interface Skill<TDomain extends string> where TDomain narrows available references, rules, and environment requirements.

3. The Vision

What does perfection look like? A data model where:

  • Invalid states are unrepresentable — If a skill is missing required fields, TypeScript refuses to compile. If a cross-reference points to a non-existent skill, the type checker catches it.
  • Skills are composable, not monolithic — A skill is a bundle of references to reusable fragments. Update a fragment once, every skill that uses it improves instantly.
  • The catalog is the source of truth — README, trigger indices, domain groupings, and audit reports are all views derived from the catalog. They cannot drift out of sync because they are generated.
  • Testing is first-class — Every skill carries its own empirical test suite: trigger prompts, expected activations, and accuracy scores. Quality is measured, not guessed.
  • Dependencies are explicit — A directed graph of skill relationships enables impact analysis, transitive closure queries, and automated stale-reference detection.
  • Progressive disclosure is encoded — The agent knows the size, topic, and relevance of every resource before reading it. No more wasting context tokens on irrelevant files.

4. TypeScript Data Model

The following is not pseudocode. It is a compilable, type-safe model that uses every powerful feature of TypeScript's type system to make the design intent explicit.

4.1 Branded Types — Preventing Accidental Substitution

// A SkillName is not just any string. It has structural proof that it passed validation.
type SkillName = string & { readonly __brand: 'SkillName' };

// FilePath ensures we never pass a raw string where a validated path is expected.
type FilePath = string & { readonly __brand: 'FilePath' };

// SemverString uses template literal types to enforce major.minor.patch at compile time.
type SemverString = `${number}.${number}.${number}`;

// TriggerPhrase is distinct from description — the description IS the trigger.
type TriggerPhrase = string & { readonly __brand: 'TriggerPhrase' };

// Severity as a finite, closed union. No typos possible. No invalid values.
type Severity = 'critical' | 'high' | 'medium' | 'low';

// SkillStatus as a state machine. Transitions can be modeled with conditional types.
type SkillStatus = 'draft' | 'thin' | 'solid' | 'comprehensive';

// Quality score is a branded number, 0-100, validated at construction.
type QualityScore = number & { readonly __brand: 'QualityScore' };

4.2 Discriminated Unions — Rich Resource Typing

// Each resource variant carries its own metadata. Exhaustive switch checks are enforced.
type Resource =
  | { readonly kind: 'script'; readonly path: FilePath; readonly executable: boolean; readonly purpose: string }
  | { readonly kind: 'reference'; readonly path: FilePath; readonly topic: string; readonly lineCount: number; readonly toc?: boolean }
  | { readonly kind: 'rule'; readonly path: FilePath; readonly domain: string; readonly constraints: ReadonlyArray<string> }
  | { readonly kind: 'asset'; readonly path: FilePath; readonly mimeType: string };

// Type guards are derived automatically from the discriminant `kind`.
function isReference(r: Resource): r is Extract<Resource, { kind: 'reference' }> {
  return r.kind === 'reference';
}

4.3 Process Fragments — Composition Over Copy-Paste

// A ProcessFragment is a reusable, named, intent-typed unit of procedure.
// The generic TIntent makes fragment purpose explicit at the type level.
interface ProcessFragment<TIntent extends string = string> {
  readonly id: string;
  readonly intent: TIntent;
  readonly steps: ReadonlyArray<string>;
  readonly rationale?: string;
}

// Common fragments live in a shared registry. Skills compose by reference, not by copy.
type FragmentRegistry = Record<string, ProcessFragment>;

// Example: The "reflective-execution" fragment used by 6+ skills.
const ReflectiveExecution: ProcessFragment<'execution'> = {
  id: 'core.reflective-execution',
  intent: 'execution',
  steps: [
    'READ, UNDERSTAND, RESEARCH, REFLECT.',
    'Break this down into multiple actionable steps. Think about them again.',
    'Execute and Verify them one step at the time.',
    'Repeat until done. Keep going until everything works and you think you did a great job!',
  ],
  rationale: 'Ensures the agent consumes context before acting, preventing shallow work.',
};

4.4 The Skill Interface — Generics, Dependencies, and Lifecycle

// Skill is parameterized by TDomain, allowing language/framework-specific specializations.
// E.g., Skill<'go'> narrows references to Go-specific files and environment to Go tooling.
interface Skill<TDomain extends string = string> {
  // ─── Identity ───
  readonly name: SkillName;
  readonly directory: FilePath;
  readonly description: TriggerPhrase;
  readonly domain: TDomain;

  // ─── Lifecycle ───
  readonly status: SkillStatus;
  readonly version: SemverString;
  readonly createdAt: Date;
  readonly updatedAt: Date;
  readonly deprecated?: Date;

  // ─── Quality Metadata ───
  readonly metadata: {
    readonly tags: ReadonlyArray<string>;
    readonly languages?: ReadonlyArray<string>;
    readonly qualityScore?: QualityScore;
    readonly empiricalTests?: ReadonlyArray<{
      readonly prompt: string;
      readonly expectedSkill: SkillName;
      readonly triggered: boolean;
      readonly accuracy: number;
    }>;
  };

  // ─── Composition: Process ───
  // Skills are built from fragment references, not monolithic prose.
  readonly process: {
    readonly discovery?: ProcessFragment<'discovery'>;
    readonly analysis?: ProcessFragment<'analysis'>;
    readonly execution?: ProcessFragment<'execution'>;
    readonly validation?: ProcessFragment<'validation'>;
  };

  // ─── Dependency Graph ───
  readonly relationships: {
    readonly requires?: ReadonlyArray<SkillName>;      // Hard dependency — skill cannot function without these
    readonly references?: ReadonlyArray<SkillName>;   // Soft reference — skill suggests these as follow-ups
    readonly conflictsWith?: ReadonlyArray<SkillName>; // Mutual exclusion — activating both is an error
    readonly supersedes?: ReadonlyArray<SkillName>;   // This skill replaces older ones
  };

  // ─── Environment ───
  readonly environment: {
    readonly requiredCLIs?: ReadonlyArray<{ readonly name: string; readonly minVersion?: SemverString }>;
    readonly optionalCLIs?: ReadonlyArray<{ readonly name: string; readonly fallback?: string }>;
  };

  // ─── Resources ───
  readonly resources: ReadonlyArray<Resource>;

  // ─── Output Schema ───
  readonly outputs?: {
    readonly format: 'markdown' | 'html' | 'd2' | 'json';
    readonly schema: unknown;
    readonly template?: FilePath;
    readonly examples?: ReadonlyArray<unknown>;
  };
}

4.5 Derived Types — Views from a Single Source of Truth

// The catalog is the ONE source of truth. Everything else is derived.
type SkillCatalog = Readonly<Record<SkillName, Skill>>;

// Trigger index: a flat lookup from trigger phrase to skill. Generated, not hand-written.
type TriggerIndex = Record<TriggerPhrase, SkillName>;

// Domain grouping: filter skills by their generic domain parameter.
type DomainGroup<T extends string> = ReadonlyArray<Skill<T>>;

// Active skills: filter out deprecated. Conditional types model state transitions.
type ActiveSkill = Skill & { readonly deprecated: undefined };

// Stale skills: updated more than 90 days ago. Mapped types transform the catalog.
type StaleSkills<Catalog extends SkillCatalog> = {
  [K in keyof Catalog as Catalog[K]['updatedAt'] extends Date
    ? (Catalog[K]['updatedAt'] extends infer D
      ? D extends Date
        ? (typeof Date.now() - D.getTime() > 90 * 24 * 60 * 60 * 1000 ? K : never)
        : never
      : never)
    : never]: Catalog[K];
};

6. Validation Layer — Making Invalid States Unrepresentable

Validation should not be a runtime script you run occasionally. It should be encoded in the type system so that every edit is checked at compile time.

// ValidatedSkill is an intersection type that requires proof of integrity.
// You cannot construct a ValidatedSkill without passing all checks.
type ValidatedSkill = Skill & {
  readonly __validated: true;
  // Proof that directory name === frontmatter name
  readonly __directoryMatchesName: true;
  // Proof that every referenced file exists on disk
  readonly __allReferencesExist: true;
  // Proof that every SkillName in relationships resolves to an entry in the catalog
  readonly __allRelationshipsResolvable: true;
  // Proof that the description is a trigger, not documentation
  readonly __descriptionIsTrigger: true;
};

// Conditional type: given a raw skill, can we prove it is valid?
type Validate<S extends Skill, Catalog extends SkillCatalog> =
  S['name'] extends infer N
    ? N extends string
      ? N extends keyof Catalog
        ? (Catalog[N]['name'] extends N ? ValidatedSkill : never)
        : never
      : never
    : never;

// Utility: extract all broken references across the entire catalog.
type BrokenReferences<C extends SkillCatalog> = {
  [K in keyof C]: C[K]['relationships']['requires'] extends ReadonlyArray<SkillName>
    ? C[K]['relationships']['requires'][number] extends infer R
      ? R extends keyof C ? never : R
      : never
    : never;
}[keyof C];

In practice, these types are backed by a zero-dependency validation script that walks the file system, parses YAML frontmatter, and either produces a ValidatedSkill or emits a typed error report. The script itself is generated from the TypeScript definitions — the code and the spec are the same artifact.

8. Migration Roadmap

The new model does not require rewriting all 18 skills overnight. It can be adopted incrementally — each step delivers value independently.

1

Schema-First: Add crush.json with typed skill catalog

Create a machine-readable catalog file (JSON or TS) that imports every skill's metadata. This becomes the single source of truth. README and audit docs become generated artifacts. Impact: Eliminates stale catalog data forever.

2

Validation Script: Prove structural integrity on every commit

A small TypeScript/Deno script that walks */SKILL.md, parses YAML frontmatter, checks that name matches directory, that all references/ links resolve, and that cross-skill references exist. Run it in a git pre-commit hook. Impact: Catches broken references before they reach master.

3

Fragment Registry: Extract duplicated process boilerplate

Move "READ, UNDERSTAND, RESEARCH, REFLECT" and Pareto planning logic into a shared fragments/ directory. Update skills to reference fragments by ID instead of inlining. Impact: 6 skills improve from one edit. Eliminates the brutal-self-review ↔ execution-mode contradiction.

4

Relationship Graph: Add relationships to frontmatter

Extend the YAML frontmatter with optional requires, references, and conflictsWith arrays. Start with the most obvious relationships: full-code-review → deduplicate-code, brutal-self-review → how-to-golang, go-modularize → how-to-golang. Impact: Agents can now follow skill chains automatically.

5

Environment Declarations: Add environment to frontmatter

Skills that need external CLIs (d2, art-dupl, revive, ginkgo) declare their requirements. The agent can check availability before activating the skill or suggest installation. Impact: Fewer runtime failures, better error messages.

6

Resource Metadata: Enrich references/ and scripts/ with index files

Add a machine-readable index.json (or YAML) in each subdirectory listing files with their metadata: topic, line count, has TOC, executable bit. The agent filters before loading. Impact: Smaller context windows, faster skill activation.

7

Empirical Testing: Attach test prompts to each skill

Add an empiricalTests array to frontmatter with 2-3 realistic prompts per skill. Use the skill-creator optimization loop to measure trigger accuracy. Store scores in the catalog. Impact: Data-driven description improvements. No more guessing.

8

Generic Parameterization: Refactor multi-language skills

Convert naming-review and similar skills to use domain-generic process fragments + language-specific reference files. Add a new language by adding one file, not editing the skill body. Impact: Extensibility without regression risk.

9. Conclusion

The current SKILLS data model works — barely. It is the product of organic growth from 17 raw prompt snippets into 18 skill directories. But organic growth without intentional design accumulates technical debt: duplicated prose, stale catalogs, broken references, and skills that contradict each other.

The improved model uses TypeScript's entire type system — branded types, discriminated unions, generics, composition, mapped types, conditional types, template literals — to make the design intent explicit and the invalid states unrepresentable. Skills become composable, testable, versioned artifacts with explicit dependency graphs and machine-readable metadata.

Most importantly, the migration is incremental. Each step delivers value without requiring a big-bang rewrite. Start with the catalog and validation script. Everything else follows naturally.
